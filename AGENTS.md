# Repository instructions

## Project Overview

foc-devnet is a Rust CLI that runs local Filecoin networks with FOC (Filecoin
Onchain Contracts) in Docker. It starts Lotus, miners, and databases, and
deploys contracts with Foundry.

## Architecture Patterns

### Step-Based Execution Pattern

Use the [`Step` trait and setup context](src/commands/start/step/mod.rs) for
startup operations. Keep prerequisite checks, execution, and verification in
their respective phases.

### Startup Sequence

[`src/commands/start/mod.rs`](src/commands/start/mod.rs) defines both
sequential startup and the parallel step epochs. When adding or moving a step,
update both schedules and respect dependencies between steps. Curio startup
is implemented in [`curio/`](src/commands/start/curio/).

## Directory Structure & Conventions

Resolve shared and per-run paths through [`src/paths.rs`](src/paths.rs)
instead of hard-coding the layout. When changing paths, consider existing
installations and run data.

## Smart Contract Deployment

The startup modules own [ETH account funding](src/commands/start/eth_acc_funding/),
[MockUSDFC deployment](src/commands/start/usdfc_deploy/), and
[FOC contract deployment](src/commands/start/foc_deploy/). See the
[MockUSDFC Foundry guide](contracts/MockUSDFC/README.md) for manual testing.

## Embedded Assets Pattern

[`src/embedded_assets.rs`](src/embedded_assets.rs) embeds Dockerfiles,
volume maps, and the MockUSDFC archive generated by [`build.rs`](build.rs).
When changing packaged files, update the relevant embedding and Cargo
rebuild inputs as needed.
Initialization skips Docker images that already exist; see
[`src/docker/build.rs`](src/docker/build.rs) when testing Dockerfile changes.

## Common Development Patterns

### Error Handling
- Use `Box<dyn Error>` for flexible error propagation.
- Use `crossterm::style::Stylize` where the surrounding CLI code styles output.
- Include diagnostic context, such as the path, container, or failed command.

### Docker and Lotus Commands

Keep subprocess invocations and flags in the appropriate shell helpers rather
than scattering them through orchestration code. See
[`src/docker/shell.rs`](src/docker/shell.rs) for Docker command helpers.

## Configuration System

[`src/config.rs`](src/config.rs) defines the config schema and source
locations. Use the existing config loading, saving, and validation paths rather
than hand-writing TOML or parsing source locations again.

## Testing & Debugging Commands

See the [quick start](README.md#-quick-start) for CLI usage and
[local checks](ci/README.md#local-checks) for contributor commands.
[`src/cli.rs`](src/cli.rs) defines the supported CLI flags.

## Documentation

- Keep `README.md` focused on first use; put advanced guides in [docs/](docs/README.md).
- Document what users need to do, expect, or diagnose.
- In code comments and docstrings, explain non-obvious reasons for decisions; don't restate what the code does.
- Link to the canonical guide instead of duplicating it. Verify commands and config examples.

## Code Style & Conventions

### Code Quality Policies
- Split files that would exceed 150 lines into modules.
- Keep functions at or below 15 lines and split functions that do multiple things.
- Define named constants for identifiers, timings, and other magic values.
- Add examples for complex tasks when they clarify usage.

### Module Documentation
Use a `//!` doc comment to explain why a module exists when its purpose isn't apparent from the code.

### Imports Organization
1. Standard library (`std::`)
2. External crates (`serde`, `crossterm`, etc.)
3. Internal crate modules (`crate::paths`, `crate::config`)
4. Parent/current module (`super::`, `self::`)
